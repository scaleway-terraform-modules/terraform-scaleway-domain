# Terraform / Scaleway

## Purpose

This repository is used to manage a domain on scaleway using terraform.
Beware this module *can not* be used to register a new domain. Existing domains must first be imported (see below). Refer to examples for more information.

- ### Importing an existing domain

The root zone of a domain already exists on Scaleway, so it must be imported before the module can manage it. With Terraform >= 1.5, use an `import` block in your root module, targeting the zone inside the module:

```hcl
import {
  to = module.my_domain.scaleway_domain_zone.this
  id = "example.net"
}
```

Subdomain zones (`subdomain` set) are created by the module and don't need to be imported. See the [existing-domain](examples/existing-domain) example.

- ### Transactional Email

Set `tem` to send mail from the zone with Scaleway Transactional Email:

```hcl
tem = {
  accept_tos = true
}
```

The module then creates the Transactional Email domain, publishes its DKIM, SPF and DMARC records in the zone, and waits for Scaleway to validate the domain.

> [!IMPORTANT]
> Setting `tem.accept_tos = true` accepts [Scaleway's Transactional Email terms of service](https://www.scaleway.com/en/contracts/), including its [anti-spam policy](https://tem.s3.fr-par.scw.cloud/antispam_policy.pdf), on behalf of the account running Terraform. Read them before enabling it.

Note that:

- the service is only available in region `fr-par`: the module always creates it there, whatever the region configured in the provider;
- the SPF record authorises Transactional Email and ends with `-all` by default: mail sent for the domain by other services fails SPF checks unless you list them in `spf.mechanisms` (e.g. `include:_spf.google.com`). Set `spf.all` to `~all` (softfail) or `?all` (neutral) to be less strict with other senders, e.g. for forwarded mail. A domain can only have one SPF record, so don't publish another one in the zone. SPF allows at most 10 DNS lookups per check, and each `include:`, `a`, `mx`, `ptr` or `exists:` mechanism counts, including those inside included records.

- ### DMARC

Set `dmarc` to publish your own [DMARC](https://datatracker.ietf.org/doc/html/rfc7489) policy for the zone, with or without Transactional Email:

```hcl
dmarc = {
  policy = "quarantine"
  rua    = ["dmarc-reports@example.net"]
}
```

When `dmarc` is not set, the module publishes the DMARC record generated by Transactional Email when `tem` is set, and no DMARC record otherwise. Either way, don't publish another DMARC record in the zone: a name with several DMARC records is invalid, and receivers then ignore DMARC. Reports sent to an address in another domain are only delivered if that domain authorises them (see [RFC 7489, section 7.1](https://datatracker.ietf.org/doc/html/rfc7489#section-7.1)).

- ### BIMI

Set `bimi` to publish a [BIMI](https://bimigroup.org/) record (`default._bimi`) in the zone, e.g. `bimi = { logo_url = "https://example.net/logo.svg" }`. Publishing the record is not enough: mail clients only display the logo when all the following requirements are met, and the module can only check some of them.

- The DMARC policy of the domain in the `From:` address is enforced: `p=quarantine` (without a `pct` below 100) or `p=reject`, and no `sp=none`.
- The DMARC policy of its parent (organizational) domain is enforced too. When the module manages a subdomain (`subdomain` set), e.g. `contact.example.net`, `example.net` must publish an enforced DMARC record, which is outside of this module. If the subdomain zone has no DMARC record of its own, receivers apply the parent domain's `sp=` (or `p=`) policy to it.
- Messages pass DMARC: they are signed with DKIM, or pass SPF, for the sending domain.
- Some mailbox providers have additional requirements, such as a Verified Mark Certificate or Common Mark Certificate (`bimi.vmc_url`).

Where the DMARC record comes from:

- **With `dmarc` set**, the module publishes that policy (see [DMARC](#dmarc)), and rejects `bimi` when it isn't enforced. Use e.g. `dmarc = { policy = "quarantine" }`.
- **With `tem` set and no `dmarc`**, the module publishes the DMARC record generated by Transactional Email, and switches its policy from `p=none` to `p=quarantine` when `bimi` is set.
- **Otherwise**, the module publishes no DMARC record: set `dmarc`, or publish one outside of the module. For a subdomain, the parent domain's policy applies when the subdomain has no DMARC record, if it's enforced and has no `sp=none`.

See the [BIMI specification](https://datatracker.ietf.org/doc/html/draft-brand-indicators-for-message-identification) for details.

- ### MX records

By default, the module creates a single MX record pointing to `blackhole.scw-tem.cloud.`, Scaleway's blackhole server, which rejects all incoming mail. This suits domains that only send mail through Transactional Email, and the record is created even when `tem` is not set. If the domain receives mail, set `mx_servers.servers` to your own servers, or to `[]` to manage MX records outside of this module. Check the existing MX records before applying on an imported domain: records not managed by Terraform are kept, and the blackhole server would be added next to them.

## Usage

- Setup the [scaleway provider](https://www.terraform.io/docs/providers/scaleway/index.html) in your tf file.
- Include this module in your tf file. Refer to [documentation](https://www.terraform.io/docs/modules/sources.html#generic-git-repository).

```hcl
module "my_domain" {
  source  = "scaleway-terraform-modules/domain/scaleway"
  version = "~> 2.1"

  domain = "example.net"
}
```

See the [examples](examples) folder for runnable configurations covering the most common use-cases (importing an existing domain, managing a subdomain, setting up Transactional Email with external MX servers).
